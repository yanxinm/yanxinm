# 任务交付标准流程

## 原则

每次完成用户交代的任务后，按以下 10 点格式输出**任务验收单**。将 **已完成** 和 **已验证** 分开说明。

---

## ⚠️ 主动汇报纪律（CRITICAL — 用户多次强调）

用户对此有明确期望：**不要等用户问才报进度和结果。** 沉默等于失职。

### ❌ 反面教材（来自真实教训）

以下行为都会触发用户不满，务必刻在脑子里：

| 错误行为 | 用户反应 | 正确做法 |
|---------|---------|---------|
| 任务跑完不吭声，等用户问"结果呢" | "验证结果没有主动告诉我" | 完成后立即主动推送完整验证报告 |
| 只报"完成"，不报具体数据和证据 | "要我问你才回复" | 把实际测试输出、搜索结果贴出来 |
| 长时间任务中途无任何进度通报 | "你要定期告知我进度" | 每完成一个阶段就报进展 |
| 任务失败后悄无声息 | — | 立即解释失败原因+替代方案 |
| 找到答案后反问"要我执行吗？" | "怎么没动静了？" | 能直接执行的不要反问确认，执行完再汇报 |
| 启动后台任务（install/build/download）后沉默等待，3分钟+无进展反馈 | "怎么没动静了？""任务中断了吗？" | 每 1-2 分钟 poll 一次进度，主动告知「XX 进行中，已完成 YY%」 |
| 工具调用被安全拦截（blocked）后不告知用户，静默跳过 | "任务中断了吗？" | 被 blocked 不等于不用管——立刻告知「XX 被拦截了，换种方式」并继续推进 |

### ⚠️ 特别场景：用户说"没收到定时任务报告"

当用户反馈「昨天六点后就没收到××报告」时：

1. **先查再解释**——不要直接说"哦可能是网络问题"。跑 `cronjob(action='list')` 确认任务是否执行，查 `last_delivery_error`
2. **区分"没跑"和"没投到"**——如果任务跑成功了但投递失败，把实际结果补上（手动跑健康检查/备份等）
3. **用表格呈现执行 vs 投递的差异**——让用户清楚看到哪步成功了、哪步失败了
4. **给出修复选项**——减频 / 换通道 / 重启，让用户决策
5. **总结规律**——如果连续多轮投递失败，说明不是偶发，是持续性通道问题

详细诊断流程见 `hermes-base-operations` 中「Cron 定时任务投递排障」一节。

### ✅ 正确做法

#### 长时间任务（>30秒）的进度通报

- **启动时**：告知用户预计耗时（"大约需要 X 分钟"）
- **每完成一个阶段或每隔 2-3 分钟**：主动报进度（"已处理 XX/YY，约 Z%"）
- **不要沉默超过 3 分钟** 而不向用户输出任何信息

#### 任务完成后：立刻主动交付验证报告

- 完成 = 未完成。**验证通过才算完成，而且你要主动证明。**
- **把实际输出贴出来**——不是"已通过"，而是把 curl 返回的 JSON、命令的运行结果、关键截图路径等证据贴到回复中
- 关键指标用表格呈现（比如搜索命中数、召回率、处理条数）
- 如果用户需要看图看数据，提供 MEDIA: 路径或实际引用
- 区分"做了什么"和"验证了什么"——后者才是用户关心的

#### 失败必须主动汇报

- 不要悄无声息地跳过或等待用户发现
- 立即告知：什么失败了、原因、替代方案

## 验收单模板

### 1️⃣ 目标是什么

用户让你做这件事的原始目标是什么简述。

### 2️⃣ 实际执行了哪些步骤

按时间顺序列出每一步操作，可以是：搜索信息、阅读文档、安装依赖、修改配置、创建文件等。

### 3️⃣ 运行了哪些命令

列出本次执行中运行的所有 shell 命令（包括 git clone、pip install、apt install、node 脚本等），方便用户核查。

### 4️⃣ 查看或修改了哪些文件

列出浏览过或修改过的文件路径，区分增/删/改/软链接等操作。

### 5️⃣ 哪些地方没有修改

明确标记**未完成**或**未触及**的部分，例如：暂未安装的可选依赖、因权限不足跳过的地方、因超时中断的下载步骤。

### 6️⃣ 现在怎么验证是否成功

给出用户可以手动验证的方法（不是"让 AI 跑一遍"），告诉用户去哪里看什么来确认。

### 7️⃣ 验证命令是什么

可以直接 copy-paste 的 shell 命令，用户运行后即可验证。

### 8️⃣ 成功时应该看到什么结果

描述验证命令成功时的预期输出，帮助用户区分"成功了"和"出问题了"。

### 9️⃣ 如果验证失败，下一步查哪里

列出常见的失败症状和对应的排查方向，让用户或后续 agent 知道从哪里入手诊断。

### 🔟 如果需要回退，怎么回退

完整的回退操作步骤，包括删除文件、移除软链接、卸载软件包等，确保可以干净回滚。

## 使用场景

- **安装/配置类任务**（如装软件、配环境、部署服务）— 必须包含完整的验证和回退部分
- **文件处理类任务**（如转换文档、修改文件）— 重点列出修改了哪些文件、未改哪些
- **查询/调研类任务**（如搜资料、查版本）— 可以不包含回退部分，但需列出来源
- **代码开发类任务** — 参考 `requesting-code-review` skill 的验证流程

## 注意事项

- 验收单不是汇报！用户不需要过程细节（如"我搜索了XXX结果"），而是**交付物清单**
- "已验证"部分必须在用户能复现的前提下写，不能依赖 agent 内部状态
- 如果有**不确定**的地方（如网络不稳定导致部分未安装），必须在第5点标明
- 如果任务简单（如回答一个问题），验收单可精简，但至少包含：做了什么、怎么验证、失败了查哪
